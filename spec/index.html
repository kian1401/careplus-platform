۳.۲ الگوریتم تخصیص هوشمند (Smart Dispatch)

تخصیص در سه مرحله انجام می‌شود: (الف) تولید فهرست کاندید با جست‌وجوی مکانی و فیلتر صلاحیت، (ب) امتیازدهی چندمتغیره، (ج) پیشنهاد مرحله‌ای و مدیریت پذیرش/رد.

الف) تولید کاندیدها (Candidate Generation)

-- فیلتر اولیه: مکانی + صلاحیت + ظرفیت + تعارض زمانی
WITH cand AS (
  SELECT p.provider_id,
         ST_Distance(p.last_location, o.location) / 1000.0 AS dist_km,
         p.rating_avg, p.acceptance_rate, p.on_time_rate,
         p.repeat_customer_bonus, p.tier,
         ci.capacity_free_slots_today,
         EXISTS (SELECT 1 FROM provider_equipment e
                 WHERE e.provider_id = p.provider_id
                   AND e.equipment_id = ANY(o.equipment_required)) AS has_equipment
  FROM provider_profile p
  JOIN provider_service_area psa ON psa.provider_id = p.provider_id
  JOIN city_service_zone z    ON z.zone_id = psa.zone_id AND z.active
  JOIN order o                ON o.order_id = :order_id
  JOIN provider_capacity ci   ON ci.provider_id = p.provider_id
  WHERE p.status = 'ACTIVE'
    AND p.verified_level >= :min_level
    AND p.last_location && ST_Expand(o.location::geometry, :radius_meters)::geography
    AND p.skills @> o.skills_required                       -- مهارت‌ها پوشش داده شود
    AND NOT EXISTS (SELECT 1 FROM booking b               -- تعارض تقویم
                    WHERE b.provider_id = p.provider_id
                      AND b.time_range && o.time_range)
    AND p.blocked_until IS NULL
  ORDER BY p.last_location <-> o.location
  LIMIT 200
)
SELECT * FROM cand;

ب) تابع امتیازدهی (Ranking Score)

Score(p, o) =
      w1 * S_distance(p,o)        // نزدیکی: 1 - norm(dist/radius)  ، وزن پیشنهادی 0.26
    + w2 * S_quality(p)           // کیفیت: ترکیب امتیاز چندبعدی + روند 90 روز اخیر ، 0.18
    + w3 * S_acceptance(p,o)      // نرخ قبولی در همین دسته/منطقه (نه کلی) ، 0.14
    + w4 * S_reliability(p)       // آن‌تایم بودن، نرخ لغو، نرخ بازکاری ، 0.12
    + w5 * S_equipment(p,o)       // تطابق تجهیزات و خودرو/وسایل لازم ، 0.08
    + w6 * S_price(p,o)           // نزدیکی پیشنهاد قیمت به بازه تخمین پلتفرم ، 0.10
    + w7 * S_history(p,o)         // سابقه کار قبلی با همین مشتری/ساختمان ، 0.06
    + w8 * S_fairness(p)          // عدالت: جبران کم‌کاری متخصصان حاشیه‌ای ، 0.04
    + w9 * S_retention(p)         // ریسک ریزش متخصص (کمبود کار اخیر) ، 0.02
    - P_penalty(p,o)              // جریمه‌ها: ردهای اخیر همان سفارش، تعلیق موقت، فاصله غیرواقعی، …
نکته کلیدی: وزن‌ها Hyperparameter نیستند که یک‌بار تنظیم شوند؛ هر منطقه و هر دسته وزن متفاوت دارد. موتور باید A/B-Test وزن‌ها را پشتیبانی کند و معیار اصلی بهینه‌سازی، Fulfillment Rate و Time-to-Accept است، نه صرفاً رضایت.

۵.۴ چرخه حل اختلاف و بازکاری (Dispute & Rework)

  1. گزارش مشتری در پنجره ۴۸ ساعته پس از پایان کار (یا در پنجره گارانتی) → توقف آزادسازی Escrow.
  2. گفتگوی خودکار: درخواست عکس/ویدیو از دو طرف + پیشنهاد راه‌حل در سه گزینه (تعمیر مجدد رایگان، بازگشت جزئی، بازگشت کامل).
  3. پاسخ متخصص در مهلت ۱۲ ساعت؛ عدم پاسخ = تصمیم به نفع مشتری.
  4. کارشناس کیفیت برای موارد بالای سقف مبلغ یا تکرارشونده؛ امکان تشکیل جلسه ویدیویی سهم‌طرفه با ضبط.
  5. اجرا توسط موتور پول (Refund/Release/Penalty) و ثبت اثر روی رتبه و ریسک متخصص.
  6. بستن پرونده با ثبت دلیل در dispute_resolution و به‌روزرسانی Playbook پشتیبانی.

KPI این چرخه: نرخ حل در تماس اول (FCR)، میانگین زمان حل (AHT)، نرخ اختلاف بازشده در هر ۱۰۰۰ سفارش، نرخ تکرار اختلاف در همان متخصص.

۷.۲ نقشه و ردیابی زنده (Live Tracking)

  • جریان موقعیت: اپ متخصص هر ۵–۱۵ ثانیه (و در حالت حرکت با فاصله محور) موقعیت را با حداقل بایت ارسال می‌کند → Kafka → سرویس Location → Redis Geo + سری‌زمانی برای بازپخش مسیر.
  • نمایش به مشتری: مسیر، ETA پویا، نام/عکس متخصص، پلاک خودرو یا مدل موتور، دکمه تماس امن و چت. «اشتراک مسیر زنده» با یک پیوند امن برای اعضای خانواده (اختیاری).
  • حریم خصوصی متخصص: ثبت موقعیت فقط در بازه فعال سفارش (از پذیرش/حرکت تا پایان کار)، نمایش متناسب با مرحله سفارش (مثلاً پیش از حرکت، فقط ETA)، توقف صریح با دکمه و امکان حذف سرگذشت مسیر پس از دوره نگهداری.
  • مسیریابی: سرویس مسیریابی داخلی یا نقشه‌های بومی (نشان، بلد، Map.ir) با امکان انتخاب صریح؛ محاسبه ETA بر پایه ترافیک لحظه‌ای و وسیله (موتور/خودرو).
  • ضدتقلب موقعیت: تشخیص Mock Location، جهش‌های غیرممکن (سرعت باورنکردنی)، عدم مطابقت با WiFi/شبکه ثبت‌شده → پرچم ریسک.

۷.۴ Push Notification و اطلاع‌رسانی

  • کانال‌ها: Push (FCM/APNs + سرویس جایگزین بومی)، SMS (دو تأمین‌کننده برای تحمل خطا)، ایمیل، WhatsApp/Telegram برای فاکتور و رسید (اختیاری)، پیام درون‌برنامه‌ای.
  • سرویس Notification مستقل: قالب‌ها در CMS، اولویت‌بندی صف (ERO/معمولی)، ضداسپم (سقف روزانه، ساعات مجاز، ترجیحات کاربر)، زمان‌بندی بر پایه منطقه زمانی، پیگیری رویداد ارسال/تحویل/کلیک.
  • رویدادهای حیاتی (با اولویت بالا): پیشنهاد فوری سفارش، لغو سفارش، تغییر زمان، تخصیص مجدد، ورود متخصص به محله، اعلان امنیتی ورود جدید.
  • قاعده: هر رویداد مهم باید «مسیر جایگزین» داشته باشد؛ اگر Push نشد → SMS؛ اگر پیامک هم نرسید → تماس خودکار اپراتور برای سفارش‌های بالای سقف.

۸.۱ قواعد عمومی مدل داده

قواعد پایه

  • کلید اصلی: UUIDv7 (مرتب بر پایه زمان ⇒ ایندکس کاراتر)؛ برای جداول پرسرویداد، کلید مرکب (created_at, id).
  • مبالغ: BIGINT در واحد خرد (ریال) + ستون currency CHAR(3)؛ هیچ‌گاه FLOAT برای پول.
  • زمان: همه timestamptz به UTC؛ نمایش بر پایه منطقه کاربر در لایه اپ.
  • حذف نرم: deleted_at؛ نگه‌داری سابقه تغییرات روی جداول مالی و پروفایل متخصص با audit_log.
  • هر جدول: created_at, updated_at, created_by (هر جا معنا دارد).
  • Enumها به‌صورت CHECK + جدول Lookup برای مقادیر قابل مدیریت از پنل.

پارتیشن‌بندی و نگه‌داری

  • پارتیشن ماهانه: order_event, provider_location_ping, notification_log, ai_inference, audit_log (۷ سال برای مالی، ۱۸ ماه برای فنی).
  • جداول داغ (سفارش باز، موقعیت متخصص) در حافظه/Redis و جدول اصلی فقط وضعیت پایدار.
  • آرشیو سرد: انتقال سفارش‌های بسته‌شده > ۲۴ ماه به جداول آرشیو (کم‌هزینه، فقط‌خواندنی).
  • حذف/بی‌اثرسازی PII پس از دوره نگه‌داری قانونی؛ نگه‌داری فیلدهای تجمیعی برای تحلیل.

۸.۵ یکپارچگی، تراکنش و همگامی بین سرویس‌ها

  • Saga برای جریان مالی سفارش: (ایجاد Escrow → تخصیص → شروع کار → تکمیل → آزادسازی). هر گام یک رویداد و یک عملیات جبرانی (Compensation) دارد: شکست آزادسازی ⇒ برنگرداندن به حالت قبل، بلکه ثبت در صف escrow_pending_release با تلاش مجدد.
  • Transaction Outbox در هر سرویس: تغییر DB و رویداد در یک تراکنش، سپس انتشار تضمین‌شده به Kafka.
  • Idempotency: همه عملیات مالی با کلید یکتا (هدر Idempotency-Key) و ثبت در جدول idempotency (TTL ۷ روز).
  • Reconciliation روزانه: PSP ↔ دفتر کل ↔ بانک ↔ صورتحساب‌های مالیاتی؛ عدم تطابق ⇒ تیکت سطح ۲ مالی.

۱۰.۳ مسیرهای اصلی کاربر (Key Flows) برای تست قابلیت استفاده

  1. مسیر اضطراری (Happy Path فوری): کلیدسازی فوری → پرداخت پیش‌پرداخت → پذیرش در ۲۰ ثانیه → ردیابی زنده → پایان کار → امتیاز. معیار: تکمیل در کمتر از ۹۰ ثانیه ثبت سفارش.
  2. مسیر پروژه‌ای (Milestone): بازسازی → بازدید و پیش‌فاکتور → Escrow ۳مرحله‌ای → تأیید مرحله‌به‌مرحله → تحویل و گارانتی ۳۰ روزه.
  3. مسیر اختلاف: اتمام کار → نارضایتی → توقف Escrow → شواهد → پیشنهاد خودکار جبران → تصمیم کارشناس → ثبت اثر روی رتبه.
  4. مسیر Onboarding متخصص: ثبت‌نام → مدارک → Face Match → آزمون → قرارداد و شبا → فعال‌سازی خودکار زیر ۳۰ دقیقه.
  5. مسیر B2B: ثبت سازمان → تأیید اعتبار → ثبت سفارش توسط کارمند → تأیید مدیر → اجرا → فاکتور و تسویه ۳۰ روزه.
روش اعتبارسنجی: ۵ آزمون کاربری نگه‌داشت‌شده با مشتری واقعی و ۵ آزمون با متخصص، در دو مرحله (وایرفریم کاغذی و پروتوتایپ کلیک‌پذیر). معیار قبولی: نرخ تکمیل > ۸۰٪ بدون کمک، SUS ≥ ۷۵، خطای بحرانی ≤ ۱ مورد در هر وظیفه.
