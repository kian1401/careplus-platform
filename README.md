# سرویسا (Care+) — بسته کامل طراحی و واگذاری پلتفرم خدمات آنلاین

بسته‌ای برای واگذاری کار به پیمانکار یا تیم داخلی: از سند نیازمندی و معماری تا **کد اجرایی، مدل داده،
کاتالوگ API، نمونه اولیه کلیک‌پذیر، PDF رسمی و تحلیل عمیق ماژول تخصیص**.

نسخه ارتقایافتهٔ مدل «آچاره» — همه محتوا فارسی، RTL و بدون وابستگی به منابع اینترنتی (فونت‌ها و استایل‌ها جاسازی‌شده‌اند).

> ⚠️ **امنیت:** در پیام اولیه کاربر یک توکن GitHub (`github_pat_…`) به‌صورت عمومی قرار گرفته بود.
> این توکن هرگز استفاده، ذخیره یا بازتولید نشده است. **آن را در GitHub → Settings → Developer settings →
> Personal access tokens فوراً Revoke کنید** و یک توکن تازه با حداقل دسترسی بسازید.

## ۴) اسکلت اجرایی MVP — `mvp/`

پیاده‌سازی مرجع سه ستون اصلی سند: **قیمت‌گذاری شفاف، Escrow چندمرحله‌ای، تخصیص امتیازمحور**.
جزئیات کامل در `mvp/README.md`. خلاصه:

- **`PricingService`** — تعرفه نسخه‌دار × ضریب فوریت (۰.۹۵–۱.۳۵) × ضریب پیچیدگی + ضریب تقاضای منطقه
  (سقف ۱.۵، معاف برای خدمات امدادی) + ایاب‌وذهاب + اقلام، با **تفکیک ردیف‌به‌ردیف** و نسخه موتور قیمت.
- **`DispatchService`** — همان ۹ وزن سند، فیلترهای سخت (فاصله/مهارت/تجهیز حیاتی/ظرفیت/انسداد)،
  موج ۳ پیشنهاد با TTL ۹۰ ثانیه (فوری ۲۰ ثانیه)، حداکثر ۳ موج، نردبان تشدید و **پذیرش اتمی**؛
  هر پیشنهاد با متن «چرا این پیشنهاد برای شما» به متخصص نمایش داده می‌شود.
- **`LedgerService`** — دفتر کل دوعاملی **زنجیره‌ای با هش** (هر قید امضای قید قبلی): مشتری → Escrow →
  کمیسیون/بیمه/مالیات → کیف پول متخصص، با بازگشت وجه، تراز آزمایشی و تراکنش‌های ابطال‌پذیر.
- **`ReviewService`** — امتیاز پنج‌بعدی و رتبه‌ی نمایشی بیزی (پیش‌فرض ۳.۹، m=۱۰).
- **تعامل:** `POST /v1/orders` با `Idempotency-Key`، ۵۱ مسیر REST، رویدادها در `event_outbox` (نماینده Kafka)،
  کنسول دمو روی `/` با روایت گام‌به‌گام، شاخص‌ها، تراز دفتر کل و مرورگر رویدادها.

## ۵) تحلیل عمیق موتور تخصیص — `analysis/`

گزارش ۱۱ صفحه‌ای که با داده بازتولیدپذیر به این پرسش‌ها پاسخ می‌دهد: راهبرد امتیازمحور چه اندازه
بر «نزدیک‌ترین متخصص» و «صف سنتی» برتری دارد؟ هر وزن چقدر اثر دارد؟ نردبان تشدید چقدر می‌ارزد؟
Surge چه می‌کند؟ عدالت توزیع چه اثری بر ریزش عرضه دارد؟

یافته‌های کلیدی (اعداد از `analysis/dispatch_sim_results.json`، ۱٬۹۰۰ سفارش / ۲۶۰ متخصص):

- **گلوگاه، ظرفیت عرضه است نه فرمول:** در عرضه عادی هر سه راهبرد بالای ۹۲٪ تخصیص می‌دهند؛
  در کمبود عرضه (۴۵٪ آنلاین) همه به ۶۰٪ سقوط می‌کنند.
- **نردبان تشدید، مؤثرترین اهرم:** حذف آن ⇒ افت ۸.۵ واحد درصدی نرخ تخصیص و جهش ارجاع به اپراتور.
- **ترتیب بهینه نردبان: «شعاع → شعاع+انگیزه → انگیزه بیشتر → اپراتور»**؛ گسترش شعاع پیش از پرداخت
  انگیزه، ارزان‌تر است (صرفه‌جویی حدود ۲۹ میلیون ریال انگیزه در نمونه).
- **±۵۰٪ تغییر وزن‌ها، کمتر از ۱ واحد درصد** نرخ تخصیص را جابه‌جا می‌کند ⇒ کالیبراسیون وزن‌ها
  توجیه تأخیر راه‌اندازی نیست؛ وزن عدالت (۰.۰۴→۰.۱۰) اهرم **نگهداشت عرضه** است.
- **سناریوهای طلایی** (`analysis/golden_dispatch_cases.json`): ۶ سفارش کنترل‌شده با رتبه‌بندی کامل
  و تطابق تأییدشده شبیه‌ساز/سرویس — آماده به‌کارگیری به‌عنوان آزمون رگرسیون.


## ۵.۱) لایه هوشمندی و تجربه روان — چهار اهرم موفقیت (این دور)

افزوده‌شده به‌عنوان بخش «AI» سند (فصل ۱۷ سند HTML، ص ۷۰ PDF) و **اجراشده در MVP**:
`mvp/app/intelligence.py` + ۷ مسیر `/v1/ai/*` + پنل هوشمندی در کنسول دمو.

| اهرم | پیاده‌سازی MVP | خروجی |
|---|---|---|
| ۱) هوشمندسازی تطبیق | `MatchingIntelligence` — رتبه‌بندی مرحله ۲ روی امتیاز مرحله ۱ (۰.۴۵ پایه + ۰.۲۰ تطابق معنایی مهارت + ۰.۲۰ ریسک عدم‌حضور + ۰.۱۰ انصاف قیمت + ۰.۰۵ کیفیت ۹۰ روزه) | `GET /v1/ai/match/preview/{id}` با متن «چرا» و تغییر رتبه |
| ۲) استانداردسازی و سفارش با AI | `StandardizationService` — کاتالوگ ۷ خدمت استاندارد (کد، دامنه اجباری، اقلام، مهارت، تجهیز، زمان، گارانتی) + نگاشت متن/عکس به استاندارد | `POST /v1/ai/intake` · `GET /v1/ai/standards` |
| ۳) کنترل کیفیت پیش‌بینانه | `PredictiveQualityService` — کارت امتیاز ۹ ویژگی ⇒ باند ریسک + احتمال بازکار/اختلاف/تأخیر + مداخله با اثر مورد انتظار | `GET /v1/ai/quality/forecast/{id}` |
| ۴) تجربه روان | `ExperienceService` — «اقدام بعدی» یک‌ضربه‌ای به‌تفکیک وضعیت + گزارش گلوگاه‌ها | `GET /v1/ai/assistant/{id}` · `GET /v1/ai/ux/friction-report` |

> حاکمیت مدل (`GET /v1/ai/scorecards`): هر خروجی متن «چرا» دارد، هیچ ویژگی محافظت‌شده در رتبه‌بندی به کار نمی‌رود،
> تصمیم‌های مالی با انسان است، و هر مدل نسخه‌دار و بازگشت‌پذیر (feature flag) است.

## ۵.۲) استقرار: GitHub و Render — `render.yaml` · `DEPLOY.md` · `scripts/`

| فایل | کارکرد |
|---|---|
| `render.yaml` | Blueprint رسمی Render (سرویس `careplus-mvp`, rootDir=`mvp`, healthCheck=`/health`, frankfurt, free, autoDeploy) |
| `mvp/Dockerfile` + `mvp/.dockerignore` | تصویر اجرایی برای هر میزبان (با HEALTHCHECK و دیسک `/data`) |
| `scripts/auto_push.sh` | ساخت مخزن GitHub (در صورت نبود) + commit/push خودکار؛ کلید از `GITHUB_TOKEN` یا `~/.github_token` و **هرگز ذخیره/چاپ نمی‌شود**؛ حالت `--loop` برای انتشار مستمر (Render با هر push دوباره مستقر می‌کند) |
| `scripts/deploy_render.sh` | ساخت/به‌روزرسانی سرویس روی Render با API + پیگیری وضعیت استقرار تا `live` |
| `DEPLOY.md` | راهنمای گام‌به‌گام استقرار + جدول اشکال‌یابی مسائل رایج + چک‌لیست بررسی ۹ موردی پس از استقرار |

### وضعیت استقرار (مهم)
- **انتشار روی GitHub هنوز انجام نشده است:** توکن موجود فقط هویت را تأیید می‌کند و مجوز ساخت مخزن/نوشتن محتوا ندارد
  (`Resource not accessible by personal access token`). راه‌حل: توکن با Contents+Administration (یا کلاسیک با `repo`)،
  یا ساخت دستی مخزن خالی و ارسال آدرس آن.
- **استقرار روی Render آماده اجراست** ولی کلید Render در این نشست در دسترس نیست (آخرین درخواست با ۴۰۱ رد شد).
  کلید را یک‌بار ارسال کنید تا `bash scripts/deploy_render.sh <repo>` اجرا و آدرس عمومی تحویل شود.
- کلید لو‌رفته GitHub از پیام اول را در GitHub **باطل (Revoke)** کنید.

## ۷) فرض‌ها و محدودیت‌ها

- همه برآوردهای زمان/هزینه **برنامه‌ریزی‌محور** و نیازمند تأیید بازار؛ نرخ‌ها باید با پیمانکار نهایی شود.
- لایه هوشمندی MVP **قاعده‌محور و قابل ممیزی** است (بدون وابستگی به LLM خاص)؛ ارتقا به مدل یادگیرنده تابع داده پایلوت است.
- MVP با SQLite اجرا می‌شود؛ نقشه انتقال به PostgreSQL/PostGIS + Kafka + Redis GEO در `mvp/README.md` آمده است.
- مدل پذیرش متخصص در شبیه‌ساز **ساختاری و کالیبره‌نشده** است؛ اعداد تحلیل «جهت‌نما» هستند و در فاز پایلوت
  باید با داده واقعی پیشنهاد/پاسخ بازبرآورد شوند (طرح A/B در گزارش بخش ۴ آمده است).
- پیش از راه‌اندازی Escrow، BNPL و کار با داده هویتی، **بازبینی حقوقی مستقل** ضروری است (ریسک‌های R-01…R-12).
