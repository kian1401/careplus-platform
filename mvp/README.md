# سرویسا (Care+) — اسکلت اجرایی MVP

پیاده‌سازی مرجع و **قابل‌اجرا** برای سه ستون اصلی سند جامع: **سفارش → Escrow → تخصیص هوشمند**.
هدف این پوشه، اثبات عملی تصمیم‌های معماری سند است: قیمت‌گذاری شفاف، نگهداشت چندمرحله‌ای پول،
موتور تخصیص امتیازمحور با موج و تشدید، دفتر کل دوعاملی و امتیازدهی چندبعدی.

> این ماژول، «نمونه اولیه فنی» است نه محصول نهایی: احراز هویت ساده (OTP با کد ثابت در محیط توسعه)،
> SQLite به‌عنوان دیتابیس پیش‌فرض، و بدون Kafka/Redis واقعی (رویدادها در جدول Outbox ثبت می‌شوند).
> نقشه انتقال به PostgreSQL/PostGIS + Kafka در ادامه آمده است.

## ۱) اجرا در ۹۰ ثانیه

```bash
cd achareh-plus/mvp
pip install -r requirements.txt

# الف) دموی خط فرمان (بدون سرور، سریع‌ترین راه دیدن کل چرخه)
python3 demo.py accept                      # مسیر خوش‌بینانه: تخصیص → اجرا → آزادسازی پول
python3 demo.py reject_then_escalate        # رد موج اول → تشدید شعاع و انگیزه → پذیرش در موج ۲
python3 demo.py no_provider                 # نبود متخصص → نردبان تشدید → تخصیص دستی اپراتور
python3 demo.py accept --surge 1.4 --offline 3   # شبیه‌سازی پیک تقاضا و کمبود عرضه
python3 demo.py --json accept | head          # خروجی JSON برای اتوماسیون

# ب) سرور API + کنسول گرافیکی دمو
python3 -m uvicorn app.main:app --host 0.0.0.0 --port 8000
#   کنسول دمو : http://localhost:8000/
#   مستندات   : http://localhost:8000/docs
#   سلامت     : http://localhost:8000/health  |  http://localhost:8000/ready

# ج) آزمون‌های یکپارچه (۱۵ آزمون: قیمت، Idempotency، Escrow، تخصیص، دفتر کل، سناریوها)
python3 -m pytest tests -q
```

پیش‌نیاز: Python 3.11+ (توسعه با 3.13 انجام شده). دیتابیس پیش‌فرض `var/mvp.sqlite` و کاملاً قابل حذف است.

## ۳) منطق پیاده‌شده (قابل ممیزی)

### قیمت‌گذاری شفاف — `PricingService`
```
مبلغ = [ تعرفه پایه × ضریب فوریت × ضریب پیچیدگی ] + ضریب تقاضای منطقه + ایاب‌وذهاب + برآورد اقلام
       − تخفیف، سپس + مالیات ارزش افزوده
ضریب فوریت: EMERGENCY 1.35 | SAME_DAY 1.15 | SCHEDULED 1.00 | FLEXIBLE 0.95
ضریب تقاضا (Surge): 0.95 … 1.50 (با kill-switch و معافیت خدمات امدادی)
```
خروجی `quote` شامل **تفکیک ردیف‌به‌ردیف**، بازه حداقل/حداکثر، نسخه موتور (`ENGINE_VERSION`) و اطمینان مدل است؛
همین ساختار در فاکتور و در صفحه پرداخت مشتری استفاده می‌شود (شفافیت = کاهش اختلاف قیمت).

### تخصیص هوشمند — `DispatchService`
۹ مؤلفه با اوزان سند: فاصله ۰.۲۶ | کیفیت ۰.۱۸ | نرخ قبولی ۰.۱۴ | پایبندی ۰.۱۲ | قیمت ۰.۱۰ |
تجهیزات ۰.۰۸ | سابقه مشتری ۰.۰۶ | عدالت توزیع ۰.۰۴ | نگهداشت ۰.۰۲، منهای جریمه‌ها.
- فیلترهای سخت: فاصله، مهارت (`skills_required`)، تجهیز حیاتی (`req:`)، ظرفیت روزانه، انسداد، ردهای مکرر.
- موج‌ها: ۳ پیشنهاد هم‌زمان، TTL پیشنهاد ۹۰ ثانیه (فوری ۲۰ ثانیه)، حداکثر ۳ موج.
- نردبان تشدید: افزایش شعاع ۱.۵× → انگیزه مالی ۳٪ مبلغ به‌ازای هر موج → ارجاع به اپراتور + ثبت دلیل در `audit_log`.
- **پذیرش اتمی**: نخستین پذیرش برنده است و بقیه پیشنهادها همان لحظه باطل می‌شوند (ایندکس یگانه روی تخصیص فعال).
- **چرا به من؟** هر پیشنهاد برای متخصص با دو مؤلفه برتر توضیح داده می‌شود (`why_me_fa`).

### پول و Escrow — `LedgerService`
دفتر کل **دوعاملی و زنجیره‌ای (hash-chained)**: هر قید با هش قید قبلی امضا می‌شود، پس دست‌کاری تاریخی قابل کشف است.
```
چرخه: PENDING_PAYMENT → HELD → (PARTIALLY_RELEASED) → RELEASED → SETTLED | DISPUTED → FREEZE → REFUND
حساب‌ها: 1100 نقد | 1150 کیف پول کاربران | 2200 واسط Escrow | 2300 کیف پول متخصص |
        2400 مالیات پرداختنی | 2500 بیمه پرداختنی | 4100 درآمد کمیسیون
آزادسازی: کمیسیون (۱۳/۱۵/۱۸٪ بر پایه رتبه) + بیمه ۰.۶٪ + مالیات ۱۰٪ → خالص به متخصص
هر سفارش: EscrowHold با مبلغ، آزادشده و بازگشتی؛ اپراتور می‌تواند refund و auto-close بزند.
```

### اعتماد و کیفیت — `ReviewService`
امتیاز پنج‌بعدی (وقت‌شناسی، کیفیت، نظم/تمیزی، تطابق قیمت با فاکتور، اخلاق حرفه‌ای)،
رتبه نمایشی با **فرمول بیزی** (پیش‌فرض ۳.۹، m=10) تا متخصص تازه‌وارد با ۲ امتیاز، رتبه‌ای ناعادلانه نگیرد؛
گارانتی هر دسته (لوله‌کشی ۳۰، برق ۹۰، کولر ۷ روز) به‌صورت خودکار روی سفارش فعال می‌شود.

## ۴) سناریوهای دمو و آنچه نشان می‌دهند

| سناریو | خروجی مورد انتظار |
|---|---|
| `accept` | ۳ پیشنهاد در موج ۱ → پذیرش بهترین امتیاز → Check-in/out با عکس اجباری → آزادسازی پول → فاکتور → امتیاز ۵ بعدی |
| `reject_then_escalate` | همه پیشنهادهای موج ۱ رد می‌شوند → موج ۲ با شعاع ۶ کیلومتر و انگیزه ۳٪ → پذیرش در موج ۲ |

## ۸) گام‌های بعدی پیشنهادی

۱) اتصال به PostgreSQL واقعی با `db/schema.sql` و اجرای آزمون‌های همین پوشه روی آن.
۲) جای‌گذاری `pytest-asyncio` + آزمون همزمانی برای پذیرش اتمی (دو متخصص، یک سفارش).
۳) افزودن WebSocket برای رهگیری زنده و وضعیت پیشنهاد (رخداد `dispatch.*`).
۴) اجرای آزمون بار روی `submit-for-dispatch` با ۲۰۰ کاندید (هدف سند: P95 < 400ms).
۵) پیاده‌سازی چرخه اختلاف (`/dispute`) و آزادسازی مرحله‌ای پروژه‌های بزرگ (Milestones).
